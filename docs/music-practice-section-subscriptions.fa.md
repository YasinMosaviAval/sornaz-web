# اشتراک آزمون‌های مدرس در یک بخش

پیشنهاد اشتراک از کارت هر سه سطح در Flutter با `nodeId` همان بخش ثبت می‌شود. فقط آزمون‌های همان مدرس در آن بخش و زیرشاخه‌های حداکثر سه‌سطحی‌اش پس از پرداخت تأییدشده قابل دسترسی‌اند. خرید تکی مرحلهٔ داخلی جدید پذیرفته نمی‌شود؛ خریدهای قدیمی و اشتراک‌های بدون محدوده همان دسترسی قبلی را حفظ می‌کنند. راهنمای جاری انتشار و حذف نرم: [کنترل سطح‌ها](music-practice-level-controls-deployment.fa.md).

شناسهٔ بخش در `f_music_practice_plans.node_id` نگهداری و هنگام ساخت سفارش در `f_music_practice_orders.node_id` تثبیت می‌شود. این دو ستون فقط شناسهٔ ساختاری‌اند؛ عنوان‌ها همچنان فقط در `f_translations` هستند. تغییر پیشنهاد پس از آغاز پرداخت، محدوده، قیمت، مدت یا سهم ثبت‌شدهٔ سفارش را عوض نمی‌کند. تمدید و قفل پرداخت برای هر خریدار، مدرس و بخش مستقل است؛ callback تکراری سهم درآمد را دوباره نمی‌نویسد.

## قرارداد API و سازگاری

- `plans/propose`: فیلد اختیاری عددی `nodeId` از هر سه سطح؛ `examId` باید صفر یا خالی باشد. مجوز ایجاد و مالکیت پیشنهاد طبق قرارداد قبلی بررسی می‌شود. مدرس قیمت و مدت را پیشنهاد می‌دهد و مدیر تأیید و سهم را تعیین می‌کند.
- `catalog`: فیلد `sectionSubscriptions` فقط آمادگی ساختار این قابلیت است و مجوز مدیریت نیست. اپ پیش از ارسال پیشنهاد بخش‌محور، این علامت را بررسی می‌کند تا سرور قدیمی آن را اشتباهاً اشتراک عمومی مدرس ذخیره نکند.
- `plans?examId=…`: پیشنهادهای مناسب همان آزمون و بخش را برمی‌گرداند. پیشنهادهای بخش‌محور برای مشتریان قدیمیِ بدون این پارامتر پنهان‌اند؛ پیشنهادهای خود مدرس و بررسی مدیر حفظ شده‌اند.
- وب و Flutter هنگام خرید، پیشنهاد بخش دیگر را نشان نمی‌دهند. کنترل نهایی دسترسی، مدرس و محدودهٔ خرید در سرور انجام می‌شود.

## migration و ترتیب امن انتشار

فایل [2026_10_30_music_practice_section_subscriptions.mariadb.sql](database/migrations/2026_10_30_music_practice_section_subscriptions.mariadb.sql) را کامل از Import در MariaDB اجرا کنید؛ اجرای مجدد و حالت نیمه‌ارتقایافته پشتیبانی می‌شود. فایل فقط دو ستون nullable اضافه می‌کند، دادهٔ موجود را تغییر نمی‌دهد و DDL آن commit ضمنی دارد. روی دیتابیس اصلی اجرا نشده است.

۱. از دیتابیس و فایل‌های فعلی پشتیبان قابل بازیابی تهیه کنید. کلید امضای آفلاین و تنظیمات واقعی را حفظ کنید. درخواست‌های نوشتنی و کارهای CLI مربوط به آزمون و پرداخت را هنگام جابه‌جایی نسخه تخلیه کنید.

۲. migration را جداگانه و پس از بازبینی اجرا کنید. نتیجه باید دو ستون `node_id` برای جدول‌های بالا داشته باشد. نسخهٔ قدیمی تا زمانی که هیچ اشتراک بخش‌محوری ایجاد نشده و ستون‌ها null هستند با این افزودن سازگار است.

در phpMyAdmin ابتدا از ستون سمت چپ، دیتابیس همین سایت را انتخاب کنید و سپس تب Import همان دیتابیس را باز کنید؛ Import از صفحهٔ اصلی سرور کافی نیست. نام مقصد را با نام دیتابیس در تنظیمات خصوصی پروژه تطبیق دهید و نام فرضی را جایگزین نکنید. پیش از Import، اجرای `SELECT DATABASE();` باید نام مقصد را نشان دهد، نه `NULL`.

خطای `#1046 - No database selected` یعنی مقصد انتخاب نشده است؛ پیام «Import finished / 1 query executed» موفقیت تغییر schema را ثابت نمی‌کند. گزارش Static analysis در phpMyAdmin نیز از خطای اجرایی سرور جداست. پس از انتخاب دیتابیس، کل فایل را دوباره Import کنید؛ فایل قابل اجرای مجدد است. برای تأیید، در تب SQL همان دیتابیس اجرا کنید:

نسخهٔ فعلی فایل فقط دو `ALTER TABLE … ADD COLUMN IF NOT EXISTS` ساده دارد؛ بلوک `BEGIN NOT ATOMIC`، دستور آماده، خروجی میانی و تغییر `FOREIGN_KEY_CHECKS` ندارد. اگر phpMyAdmin بعد از نسخهٔ قبلی خطای `#2014 - Commands out of sync` نشان داد، یک بار خارج و دوباره وارد phpMyAdmin شوید و دیتابیس مقصد را انتخاب کنید. ابتدا با پرس‌وجوی زیر وضعیت را ببینید؛ اگر دو ستون موجودند، دوباره ساختن آن‌ها لازم نیست. اگر ناقص است، نسخهٔ تازه را Import یا دو دستور آن را جداگانه در تب SQL اجرا کنید. برای این migration غیرفعال‌کردن بررسی کلید خارجی لازم نیست.

```sql
SELECT TABLE_NAME, COLUMN_NAME
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME IN ('f_music_practice_plans', 'f_music_practice_orders')
  AND COLUMN_NAME = 'node_id';
```

باید دو ردیف، یکی برای هر جدول، برگردد. صفر یا یک ردیف به معنای تکمیل‌نشدن migration است. اگر با دیتابیس منتخب هنوز خطای اجرایی باقی بود، خروجی خواندنی `SELECT VERSION(), DATABASE();` برای تشخیص کافی است؛ اطلاعات اتصال یا کلیدها را منتشر نکنید.

۳. فایل‌های سرور را به این ترتیب منتشر کنید:

- `Modules/Education/Services/MusicPracticeStore.php`
- `Modules/Education/Services/MusicPracticeAccess.php`
- `Modules/Education/Services/MusicPracticePayment.php`
- `Modules/Education/Services/MusicPracticePlans.php`
- `Modules/Education/Controllers/MusicPracticeController.php`
- `assets/Education/js/music-practice.js`
- در پایان `Modules/Education/Services/MusicPracticeCatalog.php` که آمادگی قابلیت را به اپ اعلام می‌کند.

۴. قبل از فعال‌شدن ایجاد پیشنهاد بخش‌محور، اطمینان بگیرید تمام workerها و OPcache از نسخهٔ تازهٔ Access و Payment استفاده می‌کنند. سپس اپ تازه در دسترس قرار گیرد. تغییر جدیدی در Composer یا کلیدها لازم نیست. برای نصب تازه، migration اولیهٔ کاتالوگ نیز همین دو ستون را از ابتدا دارد.

پس از خرید بخش‌محور، بازگشت به نسخهٔ قدیمی Access/Payment مجاز نیست؛ نسخهٔ قدیمی محدوده را نمی‌شناسد. در صورت مشکل ایجاد پیشنهاد یا خرید تازه را متوقف و نسخهٔ سازگار را حفظ و اصلاح رو به جلو کنید. ستون‌ها و سفارش‌ها را حذف نکنید. پیش از هر خرید بخش‌محور، بازگشت فایل‌ها با باقی‌ماندن ستون‌های nullable ممکن است؛ بازیابی پشتیبان نباید پرداخت‌ها و نتایج تازه را از بین ببرد.

## آزمون

`node scripts/music-practice-section-subscriptions-test.cjs` و نسخهٔ `--mysql` روی دیتابیس موقت محلی، ارتقای schema قدیمی، اجرای مجدد migration واقعی MariaDB، حفظ خرید قدیمی، رد بخش غیرریشه و کاربر بدون مجوز، جدایی مدرس/بخش، سفارش‌های معلق مستقل، تثبیت محدوده پس از ویرایش پیشنهاد و callback تکراری را می‌آزمایند. درگاه کاملاً ساختگی است و وجه واقعی دریافت نمی‌شود. `music-practice-online-test.cjs` نیز مسیر آنلاین و رابط وب را پوشش می‌دهد.

پس از آپلود روی محیط تست، یک خرید آزمایشی با درگاه sandbox برای دو بخش یک مدرس و یک مدرس دیگر بررسی شود: فقط بخش خریداری‌شده باز شود، بخش دیگر بسته بماند و تکرار callback نتیجهٔ مالی را تغییر ندهد. این آزمون روی سرور اصلی انجام نشده است.
