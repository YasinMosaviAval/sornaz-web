# تکمیل ثبت آموزشگاه و فایل‌های خصوصی جلسه

ثبت آموزشگاه در وب و Flutter بلافاصله پایان می‌یابد. ایجاد شعبهٔ اصلی یا فرعی از «سازمان ← مدیریت شعبه‌ها» انجام می‌شود. مسیرهای قدیمی ادامهٔ ثبت‌نام باقی مانده‌اند، اما شعبه یا OTP شعبه ایجاد نمی‌کنند؛ جریان قدیمی در مرحلهٔ انتخاب شعبه نیز کامل می‌شود. کاربر مهمان برای مدیریت آموزشگاه باید وارد حساب مجاز شود.

## فایل‌های جلسه و دسترسی

دکمهٔ گیرهٔ فایل در جزئیات جلسهٔ تقویم، جلسات ترم و کلاس‌های هنرجو/مدرس قرار دارد. در Flutter در جزئیات جلسه و حضور و غیاب ترم نیز قابل استفاده است. وضعیت مجوز در هر درخواست از سرور خوانده می‌شود؛ فهرست فایل‌ها در کش آفلاین Flutter ذخیره نمی‌شود.

- حساب آموزشگاه، مدیر و منشی دارای عضویت فعال و نقش یا قرارداد معتبر در محدودهٔ مربوط می‌توانند بارگذاری کنند. مدرس باید ثبت‌نام فعال مدرس در همان ترم داشته باشد.
- هنرجو فقط با عضویت فعال و ثبت‌نام فعال در همان ترم می‌تواند فایل جلسه را ببیند و دانلود کند. ثبت حضور به‌تنهایی مجوز نیست.
- حساب شعبه فقط به جلسات همان شعبه دسترسی دارد، حتی اگر عضویت اضافه‌ای در سطح آموزشگاه برای آن ثبت شده باشد. کارکنان شعبه به شعبهٔ دیگر یا دورهٔ بدون شعبه دسترسی ندارند؛ مدیریت معتبر در سطح آموزشگاه به شعبه‌های همان آموزشگاه دسترسی دارد.
- مدیر سایت طبق کنترل دسترسی فعلی پروژه امکان مدیریت دارد. مدیریت مربوط می‌تواند فایل را حذف کند؛ مدرس فقط فایل‌های بارگذاری‌شدهٔ خودش را حذف می‌کند. حذف نرم است و بایت‌های فایل برای جلوگیری از حذف ناخواستهٔ داده حفظ می‌شوند.
- فایل با نام تصادفی ذخیره و فقط با بررسی مجوز زنده به شکل پیوست دانلود می‌شود. مسیر مطلق فایل در API برگردانده نمی‌شود. درخواست وب تغییردهنده CSRF دارد؛ API موبایل از توکن معتبر و پروکسی فعلی پنل استفاده می‌کند.
- اعتبارسنجی MIME، نام و اندازه از سیاست موجود پیوست استفاده می‌کند؛ حداکثر ۱۰۰ MiB و محدودیت کوچک‌تر تنظیمات PHP اعمال می‌شود. تصویر، PDF، متن، صوت، ویدئو و قالب‌های سند/آرشیو مجاز سیاست مشترک قابل استفاده‌اند؛ فایل اجرایی، HTML و SVG پذیرفته نمی‌شوند.
- ارسال مجدد همان محتوای فایل توسط همان کاربر در همان جلسه، فایل تکراری نمی‌سازد. شکست ثبت اطلاعات یا commit، فایل تازه را پاک می‌کند.

## پایگاه داده و ذخیره‌سازی

Migration جدید لازم نیست. اطلاعات در جدول موجود `media_files` با `disk=private`، `visibility=private`، `collection=term-session` و `fileable_type=academy_branch_course_term_sessions` ذخیره می‌شود. جدول و ستون‌های استاندارد رسانه و عضویت/ثبت‌نام پروژه باید از قبل موجود باشند؛ هیچ DDL در درخواست سایت اجرا نمی‌شود.

در تنظیمات همان هاست، `SORNAZ_SESSION_FILES_ROOT` را به مسیر **مطلق بیرون از پوشهٔ پروژه و DOCUMENT_ROOT وب‌سرور** تنظیم کنید؛ برای مثال `/srv/sornaz-private/session-files`. مقدار خالی از `../sornaz-private/session-files` در کنار پروژه استفاده می‌کند. پوشه باید برای کاربر PHP قابل نوشتن باشد و نباید از طریق alias، symlink عمومی یا تنظیم وب‌سرور منتشر شود. دسترسی پیشنهادی پوشه 0700 و فایل 0600 است؛ مالک پوشه باید کاربر PHP باشد. اگر والد پروژه خود ریشهٔ عمومی سایت است، مسیر خصوصی دیگری تعیین کنید. پیکربندی ناامن با خطای کنترل‌شده رد می‌شود.

مقدار `upload_max_filesize`، `post_max_size` و محدودیت بدنهٔ درخواست وب‌سرور باید متناسب باشد؛ API حد واقعی PHP را در `maxBytes` می‌دهد. فایل‌های خصوصی را در پشتیبان امن هاست، جدا از بستهٔ انتشار کد، حفظ کنید. فایل تنظیمات واقعی هاست و محتوای خصوصی نباید وارد Git شوند.

## ترتیب انتشار و بازگشت

۱. پوشهٔ خصوصی و دسترسی نوشتن آن را آماده کنید. سرویس‌ها و کنترلر جدید را پیش از مسیرها منتقل کنید. Autoload نسخهٔ جدید باید این چهار کلاس را بشناسد؛ PSR-4 فعلی پروژه آن‌ها را پوشش می‌دهد. در صورت استفاده از classmap authoritative، autoload همان انتشار را بازسازی کنید.

۲. مسیرهای جلسه و کنترلرهای ثبت‌نام را منتقل کنید؛ سپس کنترلر یادگیری و قرارداد پنل موبایل را منتشر کنید. تغییرات API افزایشی‌اند و مسیرهای قدیمی ثبت‌نام باقی می‌مانند.

۳. JavaScript جدید را پیش از قالب‌ها و layout استفاده‌کننده آپلود کنید، سپس قالب‌ها و سایر JavaScriptها را منتقل کنید. نسخه‌گذاری فعلی assetها بر اساس محتوا، کش فایل تغییرکرده را جدا می‌کند. Flutter پس از آماده‌شدن API منتشر شود؛ این تغییر به OMR یا قابلیت آزمایشی وابسته نیست و برای انتقال انتخابی به شاخهٔ انتشار مناسب است.

برای بازگشت، ابتدا رابط وب و نسخهٔ جدید Flutter را متوقف/برگردانید. تا وقتی کاربران Flutter جدید دارند، مسیرهای خصوصی و قراردادهای API جلسه را نگه دارید. پوشه و رکوردهای فایل‌های کاربران را حذف نکنید. برای بازگشت ثبت‌نام، فقط کنترلر/قالب‌های همان قابلیت را به نسخهٔ قبل برگردانید؛ دادهٔ آموزشگاه و شعبه را بازنویسی نکنید.

## آزمون

`node scripts/session_files_http_test.cjs` از SQLite و وب‌سرور PHP محلی با فایل‌های ساختگی استفاده می‌کند و بارگذاری multipart واقعی، دانلود خصوصی، CSRF، رد شعبهٔ دیگر، عضویت/ثبت‌نام غیرفعال، ارسال تکراری، محدودیت فایل، rollback و حذف را می‌سنجد. نگاشت شناسهٔ جلسه در API یادگیری نیز با SQL واقعی همین fixture بررسی می‌شود. `node scripts/session_files_browser_test.cjs` رابط فارسی/انگلیسی در موبایل/دسکتاپ، کنترل هنرجو، نام فایل امن و پاسخ‌های دیررس/رد دسترسی را می‌سنجد. این آزمون‌ها به دیتابیس واقعی سایت متصل نمی‌شوند و جای آزمون MySQL و تنظیمات هاست را نمی‌گیرند.

پس از آپلود روی سرور تست: ثبت یک آموزشگاه آزمایشی باید بدون مرحلهٔ شعبه کامل شود؛ از سازمان شعبه بسازید. برای یک جلسه با مدیر و مدرس فایل آزمایشی بارگذاری و با هنرجوی همان ترم دانلود کنید. درخواست همان فایل با هنرجوی ترم دیگر و حساب شعبهٔ دیگر باید 403 شود؛ تغییر شناسهٔ جلسه به جلسهٔ مجاز دیگر نباید فایل را برگرداند. URL مستقیم پوشهٔ خصوصی باید 403/404 باشد. یک فایل کوچک مجاز و یک فایل بالاتر از حد مجاز را بررسی کنید. آزمون هاست و MySQL اصلی در این تغییر اجرا نشده است.
