# پیشوند جدول‌های فریمورک و پروژه

مرحلهٔ بعدی این نسخه، [اصلاح ساختار و ادغام پرداخت شهریه](database-hardening-deployment-2026-10-04.fa.md) است. توضیحات ۱۲۱ جدول این سند مربوط به مرحلهٔ اولیهٔ تغییر نام است؛ نگاشت نهایی پس از ادغام ۱۲۰ جدول دارد. انتشار کد فعلی باید migration مرحلهٔ دوم را نیز داشته باشد.

تاریخ: ۲۰۲۶-۱۰-۰۴. مبنا، ۱۲۱ جدول باقی‌مانده پس از پاک‌سازی کاربر و بازگشت `z_user_settings` است: ۷۴ جدول فریمورک و ۴۷ جدول پروژه. گزارش ۲۰۲۶-۱۰-۰۳ وضعیت قبل از این پاک‌سازی است.

## نتیجه و قرارداد نام‌ها

۱۱۸ جدول نام جدید می‌گیرند؛ `f_settings`، `f_timezone` و `f_translations` ثابت می‌مانند. فقط پیشوندهای `f_` و `p_` حفظ شده‌اند؛ نام‌های حوزه مانند `financial_system_*` و `social_*` پیشوند محسوب نشده‌اند. برای نمونه:

| نام منطقی قبلی | نام فیزیکی جدید |
|---|---|
| users | f_users |
| academies | p_academies |
| academy_branch_courses | p_academy_branch_courses |
| financial_system_ledger_entries | f_financial_system_ledger_entries |
| financial_system_refunds | f_financial_system_refunds |
| z_user_settings | f_user_settings |
| z_user_profiles | f_user_profiles |
| z_settings | f_legacy_settings |
| settings | p_settings |
| translations | p_translations |

دو نام آخر برای جلوگیری از برخورد با جدول‌های مستقل موجود `f_settings` و `f_translations` انتخاب شده‌اند؛ هیچ ادغام یا حذف داده‌ای انجام نمی‌شود. فهرست دقیق همه نام‌ها در [CSV نگاشت](table-prefix-map-2026-10-04.csv) و مرجع اجرایی در [config/table-names.php](../../config/table-names.php) است. فریمورک طبق تعریف این کار شامل ماژول‌های عمومی مانند حساب، محتوا، شبکه اجتماعی و مالی است؛ استقلال کامل پیاده‌سازی این ماژول‌ها از آموزشگاه ادعا نشده است.

## فراخوانی جدول‌ها در کد

طبق اصلاح دسته‌بندی کاربر، `settings` و `translations` جدول پروژه هستند و نام نهایی آن‌ها `p_settings` و `p_translations` است. اگر نسخه اولیه پیشوندها قبلاً اجرا شده و نام‌های `f_content_settings` و `f_entity_translations` وجود دارند، پس از backup و بررسی نبود مقصدها، فقط [migration اصلاح دسته](migrations/2026_10_04_project_settings_translations.sql) را اجرا کنید؛ [rollback همان اصلاح](migrations/2026_10_04_project_settings_translations_rollback.sql) نیز موجود است. در دیتابیس با نام‌های اصلی، migration اصلی به‌روزشده مستقیماً نام‌های نهایی را ایجاد می‌کند و این اصلاح جدا لازم نیست. اصلاح دو جدول در دیتابیس محلی با backup خصوصی، تطبیق شمارش دقیق رکوردها و آزمون پیشوند، پشتیبان، مالی و مرز دسترسی انجام شد؛ هاست اصلی تغییر نکرده است.

پیشوند قدیمی `z_` از نام فیزیکی هر سه جدول حذف شده است. `z_settings` به `f_legacy_settings` می‌رود چون `f_settings` قبلاً موجود است؛ دو جدول دیگر `f_user_profiles` و `f_user_settings` هستند. کلید منطقی نگاشت برای سازگاری داده‌های قبلی ثابت است.

اگر نسخه اولیه migration قبلاً اجرا شده و جدول‌های `f_z_*` وجود دارند، فقط [migration اصلاحی حذف z](migrations/2026_10_04_remove_z_prefix.sql) را پس از پشتیبان و بررسی نبود مقصدها اجرا کنید؛ [بازگشت همان اصلاح](migrations/2026_10_04_remove_z_prefix_rollback.sql) نیز موجود است. اگر هنوز نام‌های اصلی `z_*` وجود دارند، migration اصلی به‌روزشده مستقیماً نام‌های نهایی را می‌سازد و migration اصلاحی لازم نیست. دیتابیس محلی با اصلاح سه جدول به‌روز شد؛ شمارش رکوردها و کوئری منطقی هر سه جدول موفق بود. روی هاست اجرا نشده است.

`Connection` از `Core\database\PrefixedPDO` استفاده می‌کند. متدهای native `prepare`، `query` و `exec` پیش از ارسال SQL، شناسه‌های جدول را با `TableNames` به نام فیزیکی تبدیل می‌کنند. این مرز مشترک کوئری مستقیم، Builder، مدل، JOIN و جدول‌های پویا را پوشش می‌دهد. نام‌های از قبل فیزیکی دوباره پیشوند نمی‌گیرند؛ جدول ناشناخته به‌طور خودکار ساخته یا حدس زده نمی‌شود. binding، transaction و قفل‌ها همان PDO هستند.

مقادیر داده‌ای مانند `translations.table_name`، `fileable_type`، هدف اعلان، قوانین امتیاز، نام مجوز و کلید API منطقی باقی می‌مانند. رشته‌ها و commentهای SQL جایگزین نمی‌شوند. بنابراین ترجمه‌ها و مجوزهای موجود به migration داده‌ای نیاز ندارند و وب و اپلیکیشن موبایل قرارداد قبلی را حفظ می‌کنند. جایگزینی سراسری نام‌ها در JSON، مسیرها، رشته‌ها یا داده‌های دیتابیس انجام ندهید.

پرس‌وجوی metadata امتیازدهی و بررسی ستون‌های تأیید آموزشگاه نام فیزیکی را استفاده می‌کنند. پشتیبان محدود آموزشگاه، فهرست فیزیکی metadata را به نام منطقی تطبیق می‌دهد ولی `INSERT`های فایل خروجی را با نام فیزیکی می‌نویسد؛ شرط‌های انتخاب ترجمه همچنان منطقی هستند. فایل پشتیبان تولیدشده برای نسخه جدید است.

## انتشار روی هاست

این migration روی دیتابیس محلی Windows اجرا شده است؛ روی سرور اصلی اجرا نشده و فایل لوکال `config/database.php` نباید آپلود شود.

۱. روی کپی سرور تست از ساختار و داده‌ها پشتیبان خصوصی کامل بگیرید. پردازش‌های وب، callbackها، cronها، workerها و ابزارهای بیرونی نویسنده را در پنجره نگهداری متوقف کنید. دسترسی‌ها و ابزارهایی که SQL مستقیم خارج برنامه اجرا می‌کنند باید نام فیزیکی جدید را بشناسند.

۲. [preflight فقط خواندنی](migrations/2026_10_04_table_prefixes_preflight.sql) را با حسابی دارای دید کامل metadata اجرا کنید: هر ۱۲۱ سطر باید `READY` باشد، چهار شمارنده object صفر و نتیجه FK بین دیتابیس‌ها خالی باشد. جدول غایب، مقصد موجود، view/trigger/routine/event یا وابستگی خارجی نیازمند migration جداگانه است. فایل تغییر نام را در این شرایط اجرا نکنید. محیطی که هنوز جدول‌های حذف‌شده قبلی را دارد، آن‌ها را با این migration خودکار حذف نمی‌کند.

۳. فایل‌های اجرایی زیر را به‌عنوان یک نسخه هماهنگ آماده کنید. سپس [migration تغییر نام](migrations/2026_10_04_table_prefixes.sql) را در SQL client/phpMyAdmin اجرا کنید. آپلود فایل SQL به‌تنهایی migration را اجرا نمی‌کند. این فایل یک `RENAME TABLE` برای ۱۱۸ جدول دارد؛ `DROP`، تغییر رکورد، تغییر FK یا `FOREIGN_KEY_CHECKS=0` ندارد. MySQL DDL با rollback تراکنش عادی برنمی‌گردد؛ روی نسخه دقیق MySQL/MariaDB مقصد ابتدا آزمایش کنید.

۴. کد هماهنگ و autoload را فعال کنید، OPcache را تازه کنید و سپس مسیرها را آزمایش کنید. در روش Composer، `composer dump-autoload --no-scripts --no-plugins` اجرا شود؛ در آپلود دستی، autoload سازگار همین نسخه منتقل شود. کد قدیمی با نام‌های جدید جدول و کد جدید با دیتابیس قدیمی هم‌زمان سرو نشوند. پس از تغییر نام، دوباره فایل forward را اجرا نکنید.

۵. تعداد رکوردهای تک‌تک جدول‌ها و روابط FK را با قبل تطبیق دهید. ورود، پروفایل و حریم خصوصی، تنظیمات حساب، شعبه، دوره/ترم، فاکتور و پرداخت، پیام‌رسانی، شبکه اجتماعی و پشتیبان آموزشگاه را بررسی کنید. دسترسی مهمان به پنل و دسترسی کاربر آموزشگاه دیگر باید همچنان رد شود. آزمایش مالی نوشتنی فقط با داده ساختگی روی سرور تست انجام شود؛ تست fixture جای آزمون درگاه واقعی نیست.

## فایل‌های همین تغییر

فایل‌های اجرایی لازم برای آپلود:

- `config/table-names.php`
- `core/database/TableNames.php` و `core/database/PrefixedPDO.php` (دو کلاس جدید)
- `core/database/connection.php` و `core/database/AcademyInsertApproval.php`
- `Modules/Analytics/Services/UserPointService.php`
- `Modules/Analytics/Services/AcademyScopedBackupService.php`
- autoload تولیدشده همین نسخه، در آپلود دستی: `vendor/composer/autoload_classmap.php` و `vendor/composer/autoload_static.php`؛ سایر وابستگی‌های `vendor/` باید با lockfile همین نسخه سازگار باشند.

فایل‌های SQL نصب مستقل که اکنون نام فیزیکی دارند، در صورت استفاده از نصب آن ماژول منتقل شوند؛ برای همین تغییر نام لازم نیست روی دیتابیس موجود دوباره اجرا شوند:

- `Modules/Social/schema.sql`، `profile-schema.sql` و `comments-schema.sql`
- `Modules/Notation/schema.sql`
- `Modules/CourseMarket/schema.sql` و `course-experience-schema.sql`

فایل‌های عملیاتی: سه SQL forward، rollback و preflight در `docs/database/migrations/2026_10_04_table_prefixes*.sql`. گزارش CSV و همین Markdown برای مرور/راهنمای مدیر است. `scripts/` و snapshotهای `*.local.json` و پشتیبان‌های `storage/backups/` جزو آپلود عادی نیستند. تغییرات قبلی ترم و داشبورد در این workspace مستقل از این فهرست‌اند و این سند مجوز انتشار ناقص آن تغییرات نیست.

migrationهای تاریخی نام منطقی قدیمی دارند. برای SQL ثابت، `php scripts/table-prefix-sql.php input.sql new-output.sql` نسخه پیشونددار می‌سازد؛ آن را پیش از اجرا بازبینی کنید. ابزار هیچ SQL اجرا نمی‌کند، فایل مقصد موجود را بازنویسی نمی‌کند و SQL پویا/metadata را رد می‌کند؛ migration دارای `PREPARE`، `EXECUTE` یا `information_schema` باید جدا برای نام فیزیکی بازبینی شود. فایل backup یا migration تغییر نام را با این ابزار تبدیل نکنید. ابزارهای قدیمی واردکردن وردپرس که از PDO مستقل استفاده می‌کنند خودکار تبدیل نمی‌شوند؛ جدول نگاشت آن‌ها طبق اعلام کاربر حذف شده است.

## بازگشت

در پنجره نگهداری و بدون ترافیک، وجود همه نام‌های جدید و نبود مقصدهای قدیمی را بررسی کنید، سپس [rollback تغییر نام](migrations/2026_10_04_table_prefixes_rollback.sql) را اجرا و کد و autoload قبلی را با هم بازگردانید. این کار نام‌ها را برمی‌گرداند و داده‌ها را حذف نمی‌کند. در شکست یا وضعیت مخلوط، قبل از retry فهرست واقعی را بررسی کنید؛ backup کامل راه بازیابی نهایی است. backup خصوصی محلی در `storage/backups/table-prefixes/` نگهداری می‌شود؛ به هاست منتقل یا عمومی نشود.

## بررسی انجام‌شده

- MySQL جدا با کپی ساختار واقعی و داده ساختگی: تغییر نام ۱۱۸ جدول، حفظ ۲۳ ستون FK، حفظ داده، binding، transaction، رد تکرار و تغییر نام معکوس موفق بود؛ آن دیتابیس آزمایشی پاک شد.
- نصب واقعی شش فایل SQL به‌روزشده روی MySQL جدا: ۲۸ جدول پیشونددار، ۲۰ ستون FK، نصب تکراری و binding از مسیر اجرایی موفق بود. آزمون قابل تکرار: `scripts/table-prefix-schema-mysql-test.php` با متغیرهای اتصال دیتابیس تست؛ در مجموعه عادی انتشار اجرا نمی‌شود.
- دیتابیس محلی پس از backup کامل: ۱۲۱ شمارش دقیق رکورد با قبل برابر و کوئری منطقی همه جدول‌ها موفق بود.
- `node scripts/run-release-tests.cjs --browser`: ۳۱ از ۳۱ موفق؛ آزمون مالی، مرز دسترسی و پشتیبان با PDO پیشونددار اجرا شده‌اند.
- HTTP واقعی محلی: `/`، `/login`، `/users`، `/course-market`، `/community` و `/community/api/posts` پاسخ ۲۰۰؛ پنل و تنظیمات حساب برای مهمان ۳۰۲ به ورود.
- `php -l` فایل‌های PHP مرتبط، کنترل syntax JavaScript و `git diff --check` موفق بودند.
- `php scripts/php-maintainability.php check` در روش‌های از قبل تغییریافته ترم، ثبت‌نام و داشبورد خطا دارد؛ هیچ روش جدید پیشوند جدول از حد عبور نکرده است. آن تغییرات خارج از این کار بازآرایی نشده‌اند.

آزمون سرور اصلی، ورود با حساب واقعی، پرداخت واقعی و callback سرویس بیرونی در این کار انجام نشده‌اند؛ انتشار روی هاست به مرحله تست و پنجره نگهداری بالا نیاز دارد.
