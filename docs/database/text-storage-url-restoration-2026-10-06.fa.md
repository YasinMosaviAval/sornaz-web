# اصلاح نهایی: حفظ URLهای قدیمی و داده‌های فنی متنی

با توضیح کاربر، هدف انتقال **متن‌های ترجمه‌پذیر** است؛ وجود TEXT برای URLهای تاریخی، JSON و تنظیمات فنی مجاز است. تشخیص قبلیِ بی‌استفاده بودن `f_posts.pinged` اشتباه بود و اصلاح شد. عملیات روی دیتابیس محلی انجام شده؛ سرور اصلی تغییر نکرده است.

## نتیجهٔ واقعی

- `f_posts.pinged` با نوع اصلی **TEXT** و مقدار دقیق هر ۴۵۶ ردیف از پشتیبان پیش از migration برگشت؛ **۸۷ مقدار غیرخالی** بازیابی شد. مقدار چندنشانی به اجزای جدید تقسیم یا کوتاه نشد. تمام فیلدهای پست‌ها، شامل تاریخ ویرایش، با پشتیبان اصلی تطبیق داده شدند. ۹۲ کامنت نیز بدون تغییر باقی ماندند.
- ۱۱ ستون فنی زیر از BLOB/LONGBLOB به نوع متنی اصلی بازگشتند؛ بایت‌های داده پیش و پس از تبدیل برابر بودند. کنترل اعتبار JSON حفظ شد.
- انتقال ۱۲ فیلد ترجمه‌پذیر به `f_translations` و `p_translations` حفظ شد؛ مسیرهای خواندن و نوشتن کد همچنان از ترجمه استفاده می‌کنند.
- ۹ تبدیل به VARCHAR حفظ شد: مسیرها و نشانی‌های فایل، دو user-agent و نام تاریخی نویسندهٔ کامنت. این مقادیر ترجمه‌پذیر نیستند و سقف طول دارند.
- اکنون **۱۲ ستون متنی خارج از جدول‌های ترجمه** وجود دارد: ۱۱ ستون فنی و `pinged`. این وضعیت مطابق هدف اصلاح‌شده است؛ متن‌های ترجمه‌پذیرِ آن ۳۳ ستون در جدول‌های اصلی باقی نمانده‌اند.

| جدول | ستون | نوع نهایی |
|---|---|---|
| f_posts | pinged | TEXT |
| f_legacy_settings | value | LONGTEXT |
| f_social_account_settings | settings_json | TEXT |
| f_tracking_user_events | event_data | LONGTEXT |
| f_tracking_user_page_views | query_params | LONGTEXT |
| f_user_points | metadata | LONGTEXT |
| f_user_settings | value | TEXT |
| p_creator_courses | curriculum | LONGTEXT |
| p_creator_course_details | metadata | LONGTEXT |
| p_creator_course_lessons | media_json | TEXT |
| p_music_sheets | metadata | LONGTEXT |
| p_music_sheets | score | LONGTEXT |

برای این داده‌ها TEXT/LONGTEXT مناسب‌تر از BLOB است: محتوا رشته یا JSON است و نوع متنی قرارداد ذخیره‌سازی را روشن‌تر می‌کند. VARCHAR برای نشانی واحد با طول محدود مناسب است؛ برای `pinged` که می‌تواند چند URL داشته باشد و داده‌های ساختاری با اندازهٔ متغیر، همان نوع متنی قبلی حفظ شد. استفاده از BLOB صرفاً برای حذف ظاهری TEXT ضرورت نداشت.

## کد و انتشار

سیاست `config/text-storage-migration.php`، ابزار `scripts/lib/TextStorageMigration.php` و CLI آن اصلاح شدند: `pinged` حذف نمی‌شود و ستون‌های فنی به نوع متنی تبدیل می‌شوند. شرط قبلی صفر بودن همهٔ ستون‌های TEXT با کنترل حذف فقط فیلدهای ترجمه‌پذیر جایگزین شد. شش تعریف schema در Social، CourseMarket و Notation نیز به TEXT/LONGTEXT برگشتند. کد مصرف‌کننده و CHECKهای JSON با نوع متنی هم سازگارند.

`scripts/lib/RestoreTextStorage.php` ابزار مدیریتی بازیابی از دیتابیس جداگانهٔ پشتیبان معتبر است؛ در درخواست وب اجرا نمی‌شود. پشتیبان قبل از اصلاح، مقایسهٔ شناسه‌های پست، تعریف ستون‌ها، داده‌های فنی و URLها وجود دارد. مرحلهٔ DDL commit ضمنی دارد و باید در زمان توقف نوشتن اجرا شود. بازیابی حاضر، تغییر نوع‌های قبلی و بازگرداندن تاریخ تاریخی پست‌ها را نیز تکمیل کرده است.

فهرست فایل‌های اجرایی انتقال متن همان [گزارش مرحلهٔ قبل](text-storage-changes-2026-10-06.fa.md) است؛ تصمیم‌های نوع داده و حذف ستون در آن گزارش با این سند جایگزین می‌شوند. ابزار بازیابی محلی به‌تنهایی برای سرور اصلی اجرا نشود؛ منبع پشتیبان باید مربوط به همان محیط و با شناسه‌های یکسان باشد. برای نصب جدید، خروجی آغازین بالا کافی است. برنامه، تنظیمات ترجمه، کلاس `EntityText` و autoload سازگار همان انتشار نیز لازم‌اند.

پس از انتشار روی محیط تست، نمایش مقاله، مصرف URLهای تاریخی، ارسال/ویرایش پیام، ویرایش دوره و نظر و رد دسترسی به گفتگوی کاربر دیگر بررسی شود. برای بازگشت، پشتیبان خصوصی پیش از همین عملیات در `storage/backups/text-storage/url-restore-20261006-151043-89a341/before/before.sql` موجود است؛ آن را روی دادهٔ تازهٔ محصول فعال وارد نکنید.
