# اصلاح ساختار و یکپارچه‌سازی پرداخت شهریه

این نسخه پس از مرحلهٔ پیشوندگذاری `f_`/`p_` اجرا می‌شود. مقصد پرداخت شهریه `f_financial_system_payments` است؛ جدول `p_academy_term_invoice_payments` فقط پس از انتقال تراکنشی، تطبیق تعداد و مقایسهٔ تمام فیلدهای اصلی حذف می‌شود. `f_legacy_settings`، دفتر کل و بازپرداخت‌ها حذف نمی‌شوند. تغییر روی هاست اصلی اجرا نشده است.

## تغییرات

- فاصلهٔ ابتدای `f_user_settings.user_setting_id` حذف و خواندن/نوشتن تنظیمات حساب هماهنگ می‌شود. تنظیم حذف‌شده هنگام ثبت مقدار جدید زنده نمی‌شود؛ سابقه حفظ می‌شود.
- `f_world_iran_counties.county_id` کلید اصلی می‌گیرد؛ `province_id` پس از بررسی دامنه به `INT` سازگار با جدول استان‌ها تبدیل می‌شود و index می‌گیرد.
- پروفایل و تنظیمات کاربر، برای هر کاربر و کلید غیر NULL فقط یک رکورد فعال دارند. ستون generated به نام `active_unique` برای رکورد حذف‌شده NULL است؛ تاریخچهٔ soft delete قابل حفظ است. استفاده از `UNIQUE(...,deleted_at)` کافی نیست.
- indexهای جست‌وجوی شعبه، عضو، فاکتور، قسط، نقش و مجوز اضافه می‌شوند. ۱۱ رابطهٔ قطعی با FK و `RESTRICT` محافظت می‌شوند؛ orphan یا نوع ناسازگار باعث توقف پیش از تغییر می‌شود. هیچ دادهٔ یتیم خودکار پاک نمی‌شود. سرعت واقعی تولید باید با `EXPLAIN` و دادهٔ سرور سنجیده شود.
- پرداخت شهریه با `record_type='academy_term'` از رسیدهای عمومی قبلی با `record_type='legacy'` جدا می‌شود. تمام مسیرهای پرداخت آنلاین، آفلاین و کنترل ویرایش فاکتور از سرویس مشترک `AcademyPaymentStore` استفاده می‌کنند. فیلدهای عمومی `payer_id`، `method`، `reference_code`، `paid_at` و `currency_id` نیز مقدار می‌گیرند.
- وضعیت شهریه همچنان `created/pending/paid/failed/canceled` است؛ وضعیت‌های قبلی رسید عمومی از جمله `completed` تغییر نمی‌کنند. enum عمومی به VARCHAR تبدیل می‌شود تا سوابق هر دو قرارداد حفظ شوند. مبلغ `DECIMAL(22,2)` کل دامنهٔ مبلغ BIGINT UNSIGNED جدول قبلی را بدون گردکردن نگه می‌دارد.
- تمام اطلاعات درگاه، token، authority، کد پیگیری، کارت، زمان‌ها، عامل‌ها و soft delete منتقل می‌شوند. پرداخت‌های قبلی جدول عمومی شناسه‌شان را حفظ می‌کنند؛ شناسه‌های شهریه با offset بعد از بزرگ‌ترین شناسهٔ عمومی قرار می‌گیرند. `source_table/source_id` نگاشت شناسهٔ قبلی را نگه می‌دارند. مراجع شناخته‌شدهٔ ترجمه، اعلان و دفتر کل تنها برای پرداخت‌های موجود منتقل می‌شوند. مراجع بیرونی یا SQL خارج برنامه باید این نگاشت را مصرف کنند؛ شناسهٔ پرداخت را به‌تنهایی شناسهٔ دائمی مشترک دو جدول فرض نکنید.
- callback قدیمی با همان token و authority معتبر باقی می‌ماند؛ callback تکراری و قفل فاکتور همان قرارداد قبلی را دارند. داشبورد فقط شهریهٔ پرداخت‌شدهٔ شعب مجاز را نشان می‌دهد؛ رسیدی که نیازمند تطبیق دستی است در فهرست واریزی عادی نمی‌آید. رسیدهای عمومی قبلی بدون تعیین مالکیت آموزشگاهی خودکار به شهریه نسبت داده نمی‌شوند.

## ترجمه‌های متعارض: تصمیم دستی

طبق انتخاب کاربر، دو گروه متعارض `p_translations` اصلاح یا حذف نمی‌شوند و UNIQUE ترجمه اضافه نمی‌شود. گزارش کامل برای انتخاب دستی در `translation-review.json` کنار پشتیبان خصوصی ایجاد می‌شود؛ شامل متن‌ها و شناسه‌ها است و نباید در Git یا وب عمومی قرار بگیرد. گزارش ساختار قبلی در [ارزیابی ادغام](database-consolidation-review-2026-10-04.fa.md) تاریخی است.

قرارداد ADR مربوط به متن‌های Social/CourseMarket هنوز نیاز به تصمیم معماری جدا دارد؛ انتقال خودکار متن‌های کاربر یا ادغام پروفایل/رسانه در این نسخه انجام نشده است. فیلد description پرداخت، اطلاعات تراکنش موجود را حفظ می‌کند و متن قابل ویرایش عمومی سایت نیست.

## ترتیب استقرار

۱. روی کپی سرور تست و نسخهٔ دقیق MySQL/MariaDB مقصد آزمون کنید. اگر پیشوندگذاری هنوز اجرا نشده، ابتدا migration پیشوند و در صورت نیاز اصلاح نام‌های `z_` و `p_settings/p_translations` را طبق [راهنمای قبلی](table-prefixes-deployment.fa.md) اجرا کنید. migration تاریخی پیشوند هنوز ۱۲۱ جدول ورودی دارد؛ نگاشت اجرایی نهایی ۱۲۰ جدول دارد: ۷۴ فریمورک و ۴۶ پروژه. rollback تغییر نام به‌تنهایی پس از حذف جدول پرداخت قابل اجرا نیست.

۲. فایل‌های migration را فقط برای اجرای CLI موقتاً در سرور قرار دهید؛ مسیر scripts/docs نباید از وب قابل اجرا/خواندن باشد. اتصال مقصد را با متغیرهای `SORNAZ_MIGRATION_DSN`، `SORNAZ_MIGRATION_USER` و `SORNAZ_MIGRATION_PASSWORD` در محیط امن تعیین کنید؛ رمز را در history فرمان یا این سند ننویسید. ابزار به‌طور خودکار تنظیمات دیتابیس سایت را انتخاب نمی‌کند.

```sh
php scripts/db-hardening-cli.php --check
```

بخش errors باید خالی باشد. موارد duplicate ترجمه صرفاً گزارش‌اند. دید کامل metadata لازم است؛ وجود view/trigger/routine/event، جدول غیر InnoDB یا FK بین دیتابیس‌ها باید جدا بررسی شود. orphan، تکرار فعال کاربر، county_id تکراری، نوع ناسازگار یا سرریز شناسه توقف ایجاد می‌کند.

۳. نوشتن وب، callback، cron، worker و ابزار بیرونی را متوقف و درخواست‌های جاری را تخلیه کنید. قفل ابزار فقط اجرای هم‌زمان migration را منع می‌کند و جای maintenance نیست. ابزار پشتیبان کامل خصوصی می‌سازد؛ یک پشتیبان مستقل و آزمودهٔ هاست نیز داشته باشید. سپس:

```sh
php scripts/db-hardening-cli.php --apply --maintenance
```

ابزار ترتیب اصلاح، انتقال، تطبیق و DROP را مدیریت می‌کند. فایل `2026_10_04_unified_payments_columns.sql` فقط توسعهٔ ستون‌های مقصد است؛ اجرای آن به‌تنهایی پرداخت‌ها را منتقل نمی‌کند. آپلود SQL نیز اجرای migration نیست. DDL تراکنش‌پذیر نیست؛ شکست بعد از ALTER ممکن است اصلاح ساختار جزئی باقی بگذارد. ابزار پس از رفع مانع قابلیت اجرای مجدد دارد؛ اگر انتقال قبلاً commit شده و DROP شکست خورده، فقط در صورت تطبیق کامل داده‌ها ادامه می‌دهد. اختلاف داده باید دستی بررسی شود.

۴. کد و autoload هماهنگ را فعال، OPcache را تازه و سپس نوشتن را باز کنید. کلاس جدید `Modules\Academy\Services\AcademyPaymentStore` باید در autoload همان نسخه حاضر باشد. برای ساخت autoload از lockfile، `composer dump-autoload --no-scripts --no-plugins`؛ برای آپلود دستی، فایل‌های تولیدشدهٔ زیر را همراه نسخه منتقل کنید.

فایل‌های اجرایی همین مرحله:

- `Modules/Academy/Services/AcademyPaymentStore.php` (کلاس جدید)
- `Modules/Academy/Services/ZarinpalPaymentService.php`
- `Modules/Academy/Services/OfflineInstallmentPaymentService.php`
- `Modules/Academy/Services/InvoiceLedger.php`
- `Modules/Analytics/Services/AdminAccountService.php`
- `Modules/Analytics/Services/AdminDashboardService.php`
- `config/table-names.php`
- `vendor/composer/autoload_classmap.php` و `vendor/composer/autoload_static.php` در روش انتقال دستی

فایل‌های عملیاتی، فقط برای اجرای migration: `scripts/db-hardening-cli.php`، `scripts/lib/DatabaseHardeningMigration.php` و `docs/database/migrations/2026_10_04_unified_payments_columns.sql`. اسکریپت آزمون MySQL و پشتیبان‌های `storage/backups/` و فایل‌های `*.local.json` جزو آپلود عادی نیستند. تغییرات مستقل قبلی workspace باید طبق بستهٔ انتشار خودشان تحویل شوند.

گزارش مالی فقط خواندنی `scripts/audit-financial-records.sql` نیز با نام‌های فیزیکی نهایی و تفکیک پرداخت شهریه هماهنگ شده است. پنج پرس‌وجوی آن با fixture در SQLite آزموده شدند؛ رسید عمومی نامرتبط از گزارش شهریه کنار گذاشته شد. این فایل ابزار بررسی است و برای اجرای عادی وب لازم نیست. هنگام بازبینی نهایی ۲۰۲۶-۱۰-۰۵ سرویس MySQL محلی اتصال را نپذیرفت؛ اجرای دوبارهٔ گزارش روی دیتابیس واقعی در این بازبینی انجام نشد و آزمون SQLite جای آن نیست. این محدودیت نتیجهٔ migration و آزمون‌های موفق قبلی را تغییر نمی‌دهد.

۵. روی سرور تست، ورود و تنظیمات حساب، ثبت پروفایل، فاکتور/قسط، پرداخت آفلاین، درخواست آنلاین و callback تکراری را با دادهٔ ساختگی بررسی کنید. همان token قدیمی باید معتبر بماند؛ authority متفاوت و فاکتور/شعبهٔ کاربر دیگر باید رد شوند. گزارش واریزی نباید رسید نامرتبط یا شعبهٔ دیگر را نشان دهد. شمارش شهریهٔ منتقل‌شده و نگاشت source_id را با پشتیبان مقایسه کنید. پرداخت واقعی و شبکهٔ درگاه بیرونی آزمون جدا می‌خواهند.

## بازگشت و گزارش آزمون

بازگشتِ ایمن در پنجرهٔ نگهداری با بازیابی `before.sql` در دیتابیس تمیز، تطبیق داده و فعال‌کردن کد و autoload قبل از این مرحله انجام می‌شود؛ واردکردن آن روی جدول‌های موجود راه rollback نیست. ابتدا روی دیتابیس جدا بازیابی و بررسی شود. اگر پس از migration پرداخت یا دادهٔ جدید نوشته شده، بازیابی snapshot آن داده‌ها را از دست می‌دهد؛ نوشتن را متوقف و سوابق بعد از migration را حفظ و دستی تطبیق کنید. فایل DROP مقصد یا حذف خودکار پرداخت جدید ارائه نشده است.

آزمون‌های انجام‌شده: ۲۷ بررسی MySQL واقعی با schemaهای محلی و دادهٔ ساختگی؛ رسید عمومی و شهریهٔ هم‌زمان، مبلغ کامل UNSIGNED، حفظ متن‌های متعارض، مراجع ترجمه/اعلان/دفتر کل/امتیاز، کلید خارجی و یکتایی فعال، تاریخچهٔ تنظیمات، خواندن داشبورد در دو آموزشگاه، رد شعبهٔ دیگر، اجرای تکراری و بازیابی کامل پشتیبان قبل و بعد از migration. دیتابیس‌های آزمایشی پس از پایان پاک می‌شوند؛ snapshot ساختگی فقط در storage خصوصی است. آزمون قابل تکرار: `scripts/db-hardening-mysql-test.php` با `SORNAZ_TEST_MYSQL_DSN/USER/PASSWORD` روی schema پیش از migration؛ این آزمون در مجموعهٔ عادی انتشار نیست و دادهٔ سایت را نمی‌نویسد.

مجموعهٔ انتشار مرورگر ۳۱/۳۱ و آزمون رفتار پرداخت ۵۷ بررسی موفق داشتند. syntax فایل‌های PHP مرتبط و JavaScript ابزار ساخت migration و `git diff --check` نیز موفق بودند. بررسی maintainability همچنان در متدهای از قبل تغییریافتهٔ ترم/داشبورد و راهنما خطا دارد؛ کلاس پرداخت جدید خطای اندازه ندارد. نتیجهٔ fixture یا MySQL محلی، تأیید پرداخت واقعی یا انتشار هاست اصلی نیست.

## نتیجهٔ اجرای محلی

migration روی دیتابیس محلی، با پشتیبان کامل و توقف موقت درخواست‌های وب، اجرا شد. ۱۲۰ جدول باقی است و شمارش دقیق همهٔ جدول‌ها با قبل تطبیق دارد؛ مجموع دو جدول پرداخت در مقصد حفظ شده است. هر دو جدول پرداخت در دادهٔ محلی پیش از انتقال خالی بودند؛ آزمون انتقال غیرخالی با رسید عمومی و شهریهٔ ساختگی روی دیتابیس جدا انجام شد. preflight پس از اجرا خطایی ندارد، ۳۴ ستون FK وجود دارد و تمام ۱۲۰ جدول نگاشت اجرایی حاضرند. دو گروه متعارض ترجمه همچنان موجودند؛ ۱۰ ردیف گزارش خصوصی با ردیف‌های پس از migration مقایسه شدند و هیچ مقدار یا زمان آن‌ها تغییر نکرده است.

پشتیبان همین اجرا: `storage/backups/database-hardening/20261004-164945-b182e0c1/before.sql`. گزارش خصوصی بررسی دستی: `storage/backups/database-hardening/20261004-164945-b182e0c1/translation-review.json`. فایل شمارش محلی در `docs/database/hardening-result.local.json` نادیده گرفته می‌شود؛ فایل‌های خصوصی نباید آپلود شوند.

پس از بازگشایی وب محلی، صفحهٔ اصلی و ورود پاسخ ۲۰۰، پنل برای مهمان ۳۰۲ و مسیر ابزار migration و گزارش خصوصی پاسخ ۴۰۳ داشتند. هاست اصلی، حساب واقعی و درگاه واقعی آزموده یا تغییر داده نشده‌اند.
