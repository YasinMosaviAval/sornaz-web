# راهنمای فایل‌های سرور و GitHub

[English version](deployment-files.md)

این راهنما برای پروژهٔ وبسایت `sornaz` و ساختار فعلی آن تهیه شده است. «نیاز نیست آپلود شود» به معنای «از سرور حذف شود» نیست. فایل‌های واقعی کاربران، تنظیمات و داده‌های سرور را هنگام انتشار حفظ کنید. آپلود در GitHub در این متن یعنی ثبت فایل در Git و ارسال commit به مخزن.

## ۱. جدول تصمیم‌گیری

| فایل یا مسیر | سرور آنلاین | GitHub |
| --- | --- | --- |
| `index.php` | لازم؛ ورودی وبسایت | ثبت شود |
| `bootstrap/`، `core/`، `config/`، `routes/` | لازم؛ همراه با سایر فایل‌های همان نسخه | ثبت شود؛ تنظیمات نباید حاوی رمز واقعی باشند |
| `Modules/`، شامل `Resources` و `Lib` داخل ماژول‌ها | لازم؛ قالب‌ها و کتابخانهٔ PHPMailer هم جزو برنامه‌اند | ثبت شود |
| `resources/` و `views/` | لازم؛ هر دو در بارگذاری قالب استفاده می‌شوند | ثبت شود |
| `assets/` شامل CSS، JS، فونت، تصویر ثابت و `assets/vendor/` | لازم؛ استثناهای رسانه و دادهٔ آزمایشی پایین را ببینید | فایل‌های ثابت برنامه ثبت شوند |
| `.htaccess` ریشه و فایل‌های حفاظتی داخل پوشه‌ها | برای Apache و هاست سازگار لازم؛ Nginx قواعد جدا می‌خواهد | ثبت شوند؛ فایل‌های مخفی را از بسته حذف نکنید |
| `composer.json` و `composer.lock` | همراه نسخهٔ انتشار باشند؛ برای نصب و بازسازی autoload | هر دو ثبت شوند |
| `vendor/` | لازم؛ روی سرور تولید شود یا نسخهٔ سازگار آن همراه انتشار منتقل شود | ترجیحاً تولیدی و خارج از Git؛ وضعیت فعلی پروژه را پایین ببینید |
| `.env` | تنظیمات مخصوص همان سرور لازم است؛ فایل لوکال را جایگزین نکنید | هرگز ثبت نشود |
| `.env.example` | برای اجرای سایت لازم نیست | با مقادیر نمونه و بدون اطلاعات محرمانه ثبت شود |
| `sornaz` | فقط در صورت استفاده از ورودی خط فرمان لازم است | ثبت شود؛ این فایل اسکریپت PHP است، نه خروجی پایگاه داده |
| `google494712e9ea54cca1.html` و `google7cd438ee4c3edccf.html` | اگر برای تأیید مالکیت همین سایت استفاده می‌شوند، حفظ شوند | در صورت تعلق به پروژه ثبت شوند |
| `storage/` | ساختار و دسترسی نوشتن لازم است؛ محتوای لوکال را دسته‌جمعی منتقل نکنید | فقط فایل‌های ساختاری و حفاظتی بازبینی‌شده مانند `.gitkeep` و `.htaccess` |
| `docs/` | برای اجرای وب لازم نیست؛ دستورالعمل‌ها و SQL لازم را جداگانه استفاده کنید | مستندات و migrationهای بدون دادهٔ خصوصی ثبت شوند |
| `scripts/` | برای اجرای عادی وب لازم نیست؛ فقط اسکریپت عملیاتی موردنیاز، پس از بازبینی و ترجیحاً خارج از ریشهٔ وب | کد ابزارها، تست‌ها و تنظیمات ثبت شوند |
| `.php-cs-fixer.dist.php`، `.prettierrc.json` | برای اجرای وب لازم نیست | ثبت شوند |
| `scripts/format-tools/package.json` و `package-lock.json` | برای اجرای وب لازم نیست | هر دو ثبت شوند |
| `scripts/php-complexity-baseline.json` | برای اجرای وب لازم نیست | ثبت شود |
| `.gitignore` و `.gitattributes` | برای اجرای وب لازم نیست؛ در checkout سرور ممکن است وجود داشته باشند | ثبت شوند |
| `.git/` | در آپلود دستی منتقل نشود؛ اگر سرور با Git منتشر می‌کند، دسترسی HTTP به آن مسدود باشد | فایل‌های داخل آن را دستی آپلود نکنید؛ Git خودش تاریخچه را منتقل می‌کند |
| `.vscode/` و `.revision/` | لازم نیست | تنظیمات شخصی و فایل‌های موقت ثبت نشوند |

**تفاوت مهم:** `assets/vendor/` کتابخانه‌های موردنیاز مرورگر است و باید منتشر شود. پوشهٔ ریشهٔ `vendor/` شامل autoload و وابستگی‌های PHP است و آن هم در زمان اجرا لازم است. `scripts/format-tools/node_modules/` فقط ابزار توسعه است و برای سایت لازم نیست.

## ۲. فایل‌های زمان اجرا و اطلاعات خصوصی

موارد زیر را از لوکال به سرور اصلی آپلود نکنید و در GitHub ثبت نکنید:

- `.env` لوکال، رمزها، کلیدهای خصوصی و توکن‌ها.
- `php-error.log`، `storage/logs/` و پروفایل‌ها یا کش مرورگر آزمایشی داخل آن.
- `storage/sessions/sess_*`؛ نشست‌ها باید متعلق به همان محیط باشند.
- `storage/backups/`، خروجی کامل دیتابیس، فایل‌های SQL حاوی دادهٔ کاربران، `docs/database/backups/` و `docs/database/sornaz database/`.
- فایل‌های کاربران در `storage/account-media/`، `storage/chat/`، `storage/course-media/` و `storage/social-media/`.
- آپلودها در `assets/media/library/` و `assets/media/chat-groups/`.
- `storage/mobile-social-stage/` و پوشه‌های `storage/notation-browser-check/`، `storage/social-web-check/` و `storage/public-apps-check/`.
- `storage/windows-build-tools/`، `storage/windows-release/` و `storage/windows-stage/`.
- `storage/code-quality/`، `scripts/format-tools/node_modules/` و فایل‌های موقت بررسی مانند `storage/apply-audio-fixes.ps1`، `storage/audio-fix-baseline.json` و `storage/theme-fix-baseline.txt`.

این مسیرها ممکن است روی سرور دادهٔ ضروری داشته باشند. در به‌روزرسانی، دادهٔ سرور را حفظ کنید؛ در انتقال به سرور جدید، رسانه‌ها و دیتابیس واقعی را با فرایند انتقال و پشتیبان‌گیری جداگانه منتقل کنید. فایل‌های حفاظتی مانند `storage/course-media/.htaccess` و `storage/social-media/.htaccess` مستثنا هستند و باید حفظ و منتشر شوند.

`assets/media/users/` در سرویس دادهٔ آزمایشی پروژه استفاده می‌شود. محتوای آن را خودکار جزو رسانهٔ انتشار ندانید. پیش از حذف یا انتقال، ارجاع‌های دیتابیس و مجوز استفاده از رسانه‌ها را بررسی کنید. فایل‌های `ATTRIBUTION.json` و `VIDEO-SOURCES.json` اطلاعات منبع رسانه‌اند؛ برای رسانه‌ای که نگه می‌دارید، اطلاعات مجوز و منبع را نیز حفظ کنید.

## ۳. وضعیت فعلی Git: موارد نیازمند پاک‌سازی

در زمان تهیهٔ این راهنما، بررسی فهرست فایل‌های ثبت‌شده نشان داد:

- ۱۲۱۷ فایل زیر `storage/logs/` هنوز در Git ثبت شده‌اند.
- ۳۱ فایل زیر `storage/account-media/` و یک فایل SQL زیر `storage/backups/` ثبت شده‌اند.
- ۱۳ فایل زیر `vendor/` ثبت شده‌اند.

افزودن مسیر به `.gitignore` فایل ثبت‌شدهٔ قبلی را از Git خارج نمی‌کند. پیش از ارسال بعدی، این موارد باید بازبینی و فایل‌های خصوصی یا تولیدی از index خارج شوند، با حفظ نسخهٔ لازم روی دیسک و سرور. حذف از آخرین commit نیز تاریخچهٔ قبلی را پاک نمی‌کند. اگر اطلاعات محرمانه قبلاً ارسال شده‌اند، بررسی تاریخچه و در صورت افشای اعتبارنامه، تعویض آن لازم است. این بررسی محلی مشخص نمی‌کند چه چیزی قبلاً به GitHub ارسال شده است.

دربارهٔ `vendor/`، ابتدا فرایند نصب قابل تکرار با Composer را برقرار کنید و سپس سیاست Git را تغییر دهید؛ حذف ناگهانی آن از بستهٔ انتشار باعث خرابی autoload می‌شود. این راهنما فایل یا index را پاک‌سازی نکرده است.

## ۴. روش انتشار پیشنهادی

1. از دیتابیس، تنظیمات و فایل‌های واقعی سرور در محل خصوصی پشتیبان بگیرید.
2. آزمون‌ها را روی نسخهٔ آمادهٔ انتشار اجرا کنید؛ راهنمای [نگهداری کد](code-maintenance.fa.md) را ببینید.
3. بسته را از کد و فایل‌های ثابت لازم در جدول بسازید. `.env` لوکال، لاگ‌ها، نشست‌ها، بکاپ‌ها و ابزارهای توسعه را وارد آن نکنید. کل پوشهٔ لوکال را بدون فیلتر ZIP نکنید.
4. روی محیط مقصد یا محیط ساخت سازگار با آن، از lockfile نصب و autoload را بازسازی کنید:

   ```sh
   composer install --no-dev --prefer-dist --optimize-autoloader --no-interaction --no-scripts --no-plugins
   composer dump-autoload --optimize --no-dev --no-scripts --no-plugins
   ```

   اگر Composer روی هاست موجود نیست، `vendor/` ساخته‌شده برای همان نسخه را همراه کد منتقل کنید. حروف بزرگ و کوچک نام فایل‌ها در Linux مهم‌اند؛ فایل‌های `bootstrap/autoload.php` و `bootstrap/class-paths.php` و کل کد باید متعلق به همان انتشار باشند. روی سرور `composer update` اجرا نکنید.
5. `.env` اصلی و داده‌های کاربران را حفظ کنید. پوشه‌های لازم زیر `storage/` را با مالکیت و مجوز نوشتن مناسب PHP ایجاد کنید؛ از مجوز همگانی `777` استفاده نکنید. انتشار نباید فایل‌های اضافی سرور را کورکورانه حذف کند.
6. فقط migrationهای لازم و بازبینی‌شده را اجرا کنید. آپلود SQL آن را اجرا نمی‌کند؛ خروجی کامل دیتابیس لوکال را روی دیتابیس اصلی import نکنید. وجود SQL در `docs/database/` به‌تنهایی به معنای امن بودن یا لزوم اجرای آن نیست.
7. قواعد دسترسی فایل‌های خصوصی را در وب‌سرور اعمال کنید. **آپلود `.htaccess` برای Nginx کافی نیست.** فایل‌های `docs/nginx-security.conf` و `docs/nginx-private-files-emergency.conf` راهنمای ادغام تنظیمات‌اند؛ قرار دادن آن‌ها در `public_html` تنظیمات را فعال نمی‌کند. [راهنمای حفاظت فایل‌های خصوصی](private-files-hosting.md) را دنبال کنید.
8. پس از انتشار، صفحهٔ اصلی، ورود، گفتگو، رسانهٔ مجاز و مسدود بودن دانلود مستقیم فایل خصوصی را بررسی کنید. در صورت نیاز OPcache را از پنل هاست تازه‌سازی کنید.

پروژه اکنون `index.php` را در ریشه دارد؛ صرفاً با تغییر document root به پوشه‌ای فرضی به نام `public/` منتشر نکنید. فایل PHP لازم برای برنامه می‌تواند روی سرور موجود باشد ولی دسترسی مستقیم HTTP به آن مسدود باشد. مسیرهای قالب `views/` نیز نباید محل نگهداری فایل محرمانه باشند.

این سند فقط راهنماست؛ هیچ فایل سرور، تنظیم Git، تاریخچه یا داده‌ای را تغییر نمی‌دهد.
