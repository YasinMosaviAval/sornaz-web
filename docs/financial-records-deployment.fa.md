# یکپارچگی مالی و حفظ سوابق آموزشی

## تغییرات این مرحله

### ۱. ویرایش ترم بدون حذف سوابق

ویرایش ترم موجود دیگر جلسات، ثبت‌نام‌ها و فاکتورها را حذف و دوباره ایجاد نمی‌کند. فرم ویرایش وب فقط عنوان، خلاصه و توضیحات را ذخیره می‌کند؛ شناسهٔ ترم، جلسه، ثبت‌نام، فاکتور، قسط و حضور‌وغیاب ثابت می‌ماند.

API موجود با `metadataOnly: true` همین ویرایش محدود را انجام می‌دهد. اگر کل فرم قبلی ارسال شود، ساختار دوره، اعضا، جلسات و شرایط مالی باید با دادهٔ ذخیره‌شده یکسان باشد؛ تغییر ساختاری با `409` رد می‌شود. وضعیت ترم از عملیات اختصاصی تغییر وضعیت و جلسات از مدیریت جلسات تغییر می‌کنند. تغییر فهرست اعضا از فرم عمومی ویرایش ترم دیگر انجام نمی‌شود.

حذف ترم دارای سوابق ثبت‌نام، جلسه یا فاکتور مسدود است. حذف دورهٔ دارای ترم، عضو دارای ثبت‌نام یا فاکتور، و شعبهٔ دارای دوره نیز مسدود شده است. برای این رکوردها از تغییر وضعیت استفاده کنید.

جلسهٔ دارای حضور‌وغیاب از مسیر ویرایش برنامه قابل تغییر یا حذف نیست. جلسهٔ ثبت‌شده به ترم دیگری منتقل نمی‌شود. سوابق لغو و جبرانی از مسیر عمومی ویرایش جلسات دست‌کاری نمی‌شوند. ثبت حضور‌وغیاب و ویرایش یا حذف همان جلسه با قفل مشترک انجام می‌شود.

### ۲. سازگاری فاکتور و اقساط

- مبلغ‌ها با محاسبات صحیح در واحد یک‌صدم بررسی و تقسیم می‌شوند؛ جمع اقساط باید دقیقاً با مبلغ فاکتور برابر باشد.
- برای مبلغ صحیح، تقسیم اقساط مبلغ صحیح تولید می‌کند. اختلاف تقسیم بین اقساط توزیع می‌شود.
- تغییر مبلغ فاکتور بدون سابقهٔ پرداخت، مبالغ اقساط موجود را در همان تراکنش تغییر می‌دهد؛ شناسهٔ اقساط حفظ می‌شود.
- وجود هر سابقهٔ درخواست پرداخت، حتی ناموفق، یا قسط پرداخت‌شده، تغییر دستی مبلغ و وضعیت را مسدود می‌کند. درخواست ناموفق ممکن است نیازمند تطبیق بانکی باشد.
- وضعیت‌های `paid` و `partial` با انتخاب دستی ایجاد نمی‌شوند. پس از پرداخت، وضعیت از مبالغ اقساط پرداخت‌شده محاسبه می‌شود.
- توضیح و عنوان فاکتور در ترجمه‌های خود فاکتور ثبت می‌شود و عنوان ترم را تغییر نمی‌دهد. فاکتورهای قدیمی تا ثبت عنوان مستقل از عنوان ترم استفاده می‌کنند.
- ثبت پرداخت بدون رسید از متد قدیمی مسدود است؛ مسیر ثبت پرداخت خارج از درگاه با مشخصات رسید و مسیر درگاه باقی مانده‌اند.
- پرداخت ریالی یا تومانی باید مبلغ صحیح مثبت داشته باشد؛ مبلغ اعشاری بی‌صدا گرد نمی‌شود.
- مغایرت مبلغ فاکتور و اقساط، شروع پرداخت را متوقف می‌کند. اگر پرداختی قبلاً در بانک تأیید شده باشد ولی هنگام callback مغایرت دیده شود، رسید پرداخت حفظ و برای بررسی دستی علامت‌گذاری می‌شود؛ قسط به‌صورت خودکار تسویه نمی‌شود.

### ۳. تراکنش‌ها و درخواست‌های هم‌زمان

ویرایش فاکتور، پرداخت آنلاین و ثبت پرداخت خارج از درگاه از قفل یکسان `invoice:<id>` استفاده می‌کنند. عملیات مربوط به یک جلسه از قفل `session:<id>` استفاده می‌کنند. در MySQL این قفل‌ها advisory lock هستند و تمام مسیرهای جدید فوق آن‌ها را رعایت می‌کنند؛ نوشتن مستقیم در دیتابیس از این کنترل عبور می‌کند.

سرویس امتیازدهی دیگر `CREATE TABLE`، `ALTER TABLE` یا ساخت index را در درخواست عادی اجرا نمی‌کند. این دستورها در MySQL می‌توانستند تراکنش مالی یا آموزشی را ناخواسته commit کنند. ساختار دیتابیس اکنون باید هنگام انتشار آماده شود.

## ترتیب انتشار

1. از دیتابیس و فایل‌های واقعی سرور پشتیبان خصوصی بگیرید.
2. فایل [آماده‌سازی ساختار امتیازدهی](database/add-point-schema-explicit.sql) را روی نسخهٔ آزمایشی دیتابیس بررسی و سپس در پنجرهٔ انتشار روی دیتابیس مقصد اجرا کنید. این فایل به جدول موجود `user_points` نیاز دارد و شامل DDL است؛ آن را بخشی از تراکنش مالی قرار ندهید. اگر داده‌های قدیمی `award_key` تکراری باشند یا ساختار index موجود متفاوت باشد، پیش از ادامه بررسی دستی لازم است؛ رکوردها را خودکار حذف نکنید.
3. فایل [گزارش مغایرت‌های قبلی](../scripts/audit-financial-records.sql) فقط `SELECT` دارد. آن را روی نسخهٔ پشتیبان یا در زمان کم‌بار اجرا کنید. پرس‌وجوی اول جدول‌هایی را نشان می‌دهد که InnoDB نیستند؛ تا بررسی این موارد، نباید به rollback آن جدول‌ها اتکا کرد. نتایج مالی و شناسه‌های کاربران را عمومی منتشر نکنید.
4. کدهای تغییرکردهٔ سرویس‌ها، کنترلرها و `assets/Analytics/js/terms.js` را با هم منتشر کنید. دو کلاس جدید `InvoiceLedger` و `TermRecordGuard` باید در بسته باشند. Composer autoload را بازسازی کنید یا فایل‌های autoload همین نسخه را همراه کد منتقل کنید:

   ```sh
   composer dump-autoload --no-scripts --no-plugins
   ```

5. در صورت نیاز OPcache و کش فایل JavaScript را تازه‌سازی کنید. با حساب مجاز، ویرایش توضیح ترم، تغییر فاکتور بدون پرداخت و رد تغییر فاکتور پرداخت‌شده را بررسی کنید.

**SQL این مرحله روی دیتابیس شما اجرا نشده است.** اگر ساختار امتیازدهی ناقص باشد، ثبت امتیاز خودکار انجام نمی‌شود و بخش مدیریت امتیازها خطا می‌دهد؛ برنامه برای رفع آن در حین پرداخت ساختار دیتابیس را تغییر نمی‌دهد. پس از انتشار، آماده بودن این بخش را نیز بررسی کنید.

## آزمون‌ها

```sh
php scripts/financial_records_test.php
php scripts/reliability_test.php
node scripts/financial_records_browser_test.cjs
node scripts/run-release-tests.cjs --browser
php scripts/php-maintainability.php check
```

آزمون‌های جدید شامل حفظ شناسه‌ها و سوابق پس از ویرایش توضیحات، رد تغییر مخرب، حفظ جمع اقساط، بازگشت کامل تغییرات هنگام خطای ذخیره، رد تغییر مبلغ با پرداخت در انتظار یا انجام‌شده، حفظ رسید بانکی دارای مغایرت و جلوگیری از DDL در تراکنش هستند. آزمون مرورگر خروجی امن فرم ویرایش و ارسال صرفاً اطلاعات توضیحی را بررسی می‌کند.

## مواردی که نیاز به بررسی عملیاتی دارند

- داده‌هایی که در گذشته مخفی، تکراری یا ناسازگار شده‌اند خودکار ترمیم نمی‌شوند. گزارش SQL برای شناسایی است؛ تطبیق مبلغ و رسید با سوابق واقعی بانک و آموزشگاه لازم است.
- تست‌ها از SQLite در حافظه و پاسخ شبیه‌سازی‌شدهٔ درگاه استفاده می‌کنند. SQL مهاجرت روی MySQL واقعی و پرداخت بانکی واقعی در این محیط اجرا نشده است.
- کنترل هم‌پوشانی زمان جلسات بین چند کلاس یا مدرس و طراحی دفتر ثبت همهٔ نسخه‌های قبلی اصلاح حضور‌وغیاب، بررسی‌های جداگانه هستند. این تغییر به معنای تأیید کامل تمام حسابداری و برنامه‌ریزی آموزشی سایت نیست.
- APK جدید ساخته نشده و انتشار روی سرور انجام نشده است.
