# چک‌لیست هم‌ارزی API وب‌سایت و اپلیکیشن فلاتر

تاریخ بررسی: ۱۴۰۵/۰۷/۱۷. این فهرست بر اساس مسیرهای نسخهٔ فعلی کد تهیه شده است. «موجود» به معنی وجود مسیر است، نه تأیید یکپارچهٔ همهٔ نقش‌ها روی سرور اصلی. هر عملیات باید با Bearer token، کنترل مالکیت در سرور، پاسخ JSON و همان قواعد اعتبارسنجی وب کار کند. انتشار روی سرور اصلی و migration در این کار انجام نمی‌شود.

## اولویت ۱: داده‌های شخصی همهٔ کاربران

- [x] موجود: `GET /api/sornaz/v1/panel` و عملیات انتخابی `/{section}/{operation}`؛ فهرست عملیات در `MobilePanelCatalog` است.
- [x] امتیازها: عملیات `my-points/list` امتیاز عمومی و تخصصی، قوانین و سوابق خود کاربر را برمی‌گرداند؛ مدیریت قوانین جدا می‌ماند.
- [x] تنظیمات: `my-settings/list|save` تنظیمات شخصی را در `z_user_settings` می‌خواند/می‌نویسد؛ ویرایش تنظیمات سراسری فقط مدیر سایت است. همگام‌سازی تنظیمات محلی مرورگر وب با این مقدار هنوز جداگانه لازم است.
- [x] گالری شخصی: `my-gallery/list|create|update|delete` شناسهٔ مالک را از حساب فعلی می‌گیرد؛ دانلود فایل خصوصی از مسیر حساب با بررسی مالکیت انجام می‌شود.
- [x] درس‌های شخصی: `my-lessons/list|create|update|delete` از همان مسیر نوشتن وب استفاده می‌کند.
- [x] برنامهٔ زمانی شخصی: `my-schedule/list|create|update|delete` گروه بازه‌ها و ممنوعیت ویرایش بازهٔ در حال استفاده را حفظ می‌کند.
- [x] امور مالی شخصی: `my-finance/list|update` فاکتور، اقساط و پرداخت‌های عضو فعلی را می‌خواند و ویرایش فاکتور را به دفتر مالی می‌سپارد.

## اولویت ۲: حساب و صندوق ارتباطات

- [x] موجود: عملیات پایهٔ حساب، پروفایل، امنیت، رسانه، پیام و اعلان در فهرست API پنل.
- [ ] تطبیق اسناد، نشست‌ها، خروجی اطلاعات ویژهٔ `user_id=1` و پاسخ‌های فایل/دانلود با کلاینت فلاتر و آزمون عملی.
- [x] فهرست و عملیات خواندن/حذف مجاز پیام‌ها و اعلان‌ها برای همهٔ کاربران؛ عملیات ایجاد و انتشار در فهرست API به نقش مناسب محدود شده است.
- [x] تغییر تماس در API توکنی: `account/contact-send|contact-verify|contact-commit` کد هش‌شده را در جدول مستقل، با زمان انقضا، سقف تلاش و مصرف یک‌باره نگه می‌دارد. اجرای migration پیش از فعال‌کردن این عملیات ضروری است.

## اولویت ۳: آموزشگاه و مدیر سایت

- [x] موجود: ورودی‌های API برای شعبه‌ها، اعضا، دوره‌ها، کلاس‌ها، ترم‌ها، حضور و غیاب، اشتراک، مالی، نقش‌ها، مجوزها، رسانه، نوشته‌ها، برگه‌ها و گزارش‌ها.
- [ ] بررسی عملیاتی هر مسیر JSON و هر نقش؛ تمایز مدیر سایت، مالک/مدیر آموزشگاه، مدیر شعبه، مدرس، هنرجو و کاربر عادی.
- [ ] حذف عملیات نمایشی یا غیرمجاز از فهرست قابلیت‌های ارسالی به فلاتر.
- [ ] عملیات پرداخت آنلاین فاکتور و اشتراک هنوز به پاسخ redirect در مسیر وب متکی است؛ قرارداد آغاز پرداخت و بازگشت در اپ باید جداگانه با درگاه آزموده شود.

## اولویت ۴: بخش‌های عمومی وب‌سایت

- [x] موجود: احراز هویت، شبکهٔ اجتماعی، دوره‌های بازار، نت‌نویسی، آموزشگاه‌های عمومی، ثبت‌نام آموزشگاه و مقاله‌ها.
- [ ] تطبیق صفحه‌به‌صفحهٔ قابلیت‌های عمومی وب و افزودن پاسخ داده‌ای برای هر قابلیت فقط-HTML.
- [ ] آزمون سازگاری با نسخهٔ فعلی فلاتر و نسخه‌های قدیمی کش‌شدهٔ اپ.
- [x] داده‌های عمومی خانه، دربارهٔ ما و تماس با ما از `GET /api/sornaz/v1/site/home|about-us|contact-us` در قالب JSON در دسترس‌اند. مسیر قدیمی `GET /api/pages` نیز به داده‌های خانه وصل شده و عملیات نوشتن قدیمی که پیاده‌سازی معتبر نداشتند پاسخ ۴۰۵ می‌دهند.
- [ ] ارسال فرم تماس از مسیر JSON موجود `/contact` باید با قرارداد فلاتر و خطاهای آن آزمون شود.

## معیار تکمیل هر ردیف

- آزمون موفقیت، خطای ورودی، توکن نامعتبر، دادهٔ کاربر/آموزشگاه دیگر و درخواست تکراری.
- کنترل داده پیش از خواندن یا نوشتن؛ فایل خصوصی فقط از مسیر دارای مالکیت.
- قرارداد پاسخ، ترجمهٔ فارسی/انگلیسی و سازگاری با کلاینت فلاتر ثبت شود.
- `php -l`، آزمون مرتبط، `git diff --check` و در پایان مجموعهٔ انتشار اجرا شود.

## ترتیب انتشار و بازگشت نسخهٔ در حال توسعه

ابتدا جدول `f_mobile_contact_challenges` را از `docs/database/migrations/2026_10_09_mobile_contact_challenges.sql` روی محیط تست با پشتیبان آماده کنید؛ پیش از انتشار مسیر `contact-*`، جدول باید روی همان محیط موجود باشد. سپس سرویس‌ها و کنترلرهای تازه، مسیرهای `Modules/Analytics/Routes/routes.php` و در پایان `MobilePanelCatalog.php` و قالب `personal-panel-sections.php` را بارگذاری کنید. نسخه‌های قدیمی اپ به مسیرهای قبلی متکی می‌مانند. برای بازگشت، ابتدا فهرست و مسیرها را به نسخهٔ پیشین برگردانید و سپس کنترلر و سرویس تازه را حذف کنید؛ جدول تازه و دادهٔ تنظیمات شخصی را در بازگشت اضطراری پاک نکنید. انتشار یا اجرای migration روی سرور اصلی در این کار انجام نشده است.
