# اصلاح پرداخت و نمایش مالی اپلیکیشن

## تغییرات

- `Modules/Academy/Services/ZarinpalPaymentService.php`: اختلاف تومان و ریال دیگر خطا نیست. مبلغ قسط از واحد فاکتور به واحد تنظیم‌شده درگاه تبدیل و همراه همان واحد ذخیره/ارسال می‌شود. تأیید زرین‌پال مبلغ ریالی می‌گیرد. تسویه با مقایسه مبلغ تبدیل‌شده انجام می‌شود؛ واحد و مبلغ خود فاکتور تغییر نمی‌کند. درخواست قبلی با واحد ذخیره‌شده خودش بازیابی می‌شود. تبدیل غیرقابل نمایش به عدد صحیح، بدون گرد کردن رد می‌شود.
- `Modules/Analytics/Services/MobilePanelCatalog.php`: وضعیت ویرایش فاکتورهای مدیریتی و شخصی، انتخاب‌گر فارسی فقط‌خواندنی است.
- `scripts/reliability_test.php`: شبیه‌سازی پرداخت دوطرفه ریال/تومان، تأیید ریالی، تسویه، بازیابی درخواست پس از تغییر تنظیم واحد، و تبدیل دقیق.
- اپلیکیشن: `lib/screens/Site/panel_finance.dart`، `panel_table_contract.dart` و `panel_resource_page.dart`: یک وضعیت فارسی در جزئیات، وضعیت فقط‌خواندنی در ویرایش، و استفاده از کارت مشترک داشبورد برای مجموع/پرداخت‌شده/مانده.
- اپلیکیشن: `lib/screens/Site/panel_presentation.dart` برچسب کارت‌های مالی؛ `panel_dashboard.dart` حذف نمایش «موارد فوری» با حفظ اقدامات نیازمند بررسی.
- اپلیکیشن: `test/panel_finance_expansion_test.dart` آزمون وضعیت، عدم امکان تغییر، کارت مشترک و حذف موارد فوری.

## بررسی‌ها

- PHP lint هر دو فایل سرویس/کاتالوگ موفق.
- `php scripts/reliability_test.php`: ۶۵ بررسی موفق، با SQLite و پاسخ شبیه‌سازی‌شده درگاه؛ بدون تراکنش واقعی.
- `php scripts/financial_records_test.php`: ۴۴ بررسی موفق.
- `php scripts/mobile_panel_parity_test.php` و `mobile_panel_dialog_test.php`: موفق، ۶۴ بخش.
- `php scripts/mobile_panel_test.php --api-only`: موفق، ایزوله‌بودن احراز هویت و مسیرها.
- Flutter: ۹ آزمون مالی مرتبط موفق با `flutter test --no-pub test/panel_finance_expansion_test.dart --name '^(?!guidance editor)'`.
- اجرای کل فایل یک شکست قبلی در آزمون `guidance editor preserves bilingual values on failure and submits the website page key` نشان می‌دهد: انتظار رنگ نیمه‌شفاف کارت راهنما با رنگ ترکیب‌شده فعلی متفاوت است. کد کارت راهنما در این تغییر دست نخورده است.
- تحلیل شش فایل Flutter خطای کامپایل نداشت؛ ۲۸ پیام سطح info از قواعد سبک موجود گزارش شد.

## استقرار و بازگشت

شاخه main وب پیش از ویرایش با origin/main همگام و به‌روز بود. ابتدا تغییر سرویس پرداخت وب و کاتالوگ مستقر شود، سپس تغییرات اپلیکیشن به‌صورت انتخابی منتقل شود. migration، تغییر merchant، تنظیم واحد پیش‌فرض، شناسه برنامه یا امضای برنامه لازم نیست. هیچ خروجی اپلیکیشن، commit، push یا پرداخت واقعی ساخته/انجام نشد. رفتار واقعی انتقال و callback روی درگاه مستقر هنوز نیازمند بررسی است.

تغییرات به OMR و ابزار تحلیل عملکرد وابسته نیستند. فایل‌های کاتالوگ و صفحه عمومی اپلیکیشن از کارهای قبلی همین محیط هم تغییر دارند؛ برای انتقال به release فقط hunkهای مربوط به مالی انتخاب شوند و AGENTS.md منتقل نشود.

برای بازگشت، hunkهای همین اصلاح را برگردانید؛ رکوردهای پرداخت موجود و currency ذخیره‌شده آن‌ها حفظ شوند. بازگرداندن سرویس قدیمی پس از ایجاد پرداخت با واحد متفاوت می‌تواند تأیید درخواست‌های در انتظار را مختل کند؛ ابتدا درخواست‌های در انتظار تسویه/تطبیق شوند.

مرجع قرارداد درخواست و تأیید: https://www.zarinpal.com/docs/paymentGateway/connectToGateway
